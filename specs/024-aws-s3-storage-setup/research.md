# Research & Technical Architecture: AWS S3 Media Storage, CORS & IAM Security Setup

**Feature**: `024-aws-s3-storage-setup` (Jira: [VS-41](https://the-three-devsketeers.atlassian.net/browse/VS-41))
**Date**: 2026-10-04

---

## 1. Technical Context & Scope Analysis

The goal of this feature is to establish the core AWS object storage foundation for Electa media assets (contestant profiles, event banners, organization logos). The architecture spans two decoupled repositories:
1. **`electa-infra` (Terraform IaC)**:
   - S3 Bucket provisioning in `ap-southeast-1` (`electa-dev-media-assets`).
   - Server-side encryption (SSE-S3 AES-256).
   - Strict public access block.
   - CORS policy configuration permitting `http://localhost:3000`, `https://*.electa.app`, and `https://*.electa.com`.
   - Dedicated least-privilege IAM service user (`electa-s3-service-user`) and IAM policy (`ElectaS3MediaPolicy`) scoped exclusively to `s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject`.
2. **`electa-fullstack` (Next.js Application)**:
   - Strong schema validation via `@t3-oss/env-nextjs` and Zod in `src/env.ts`.
   - Comprehensive `.env.example` documentation and `.env.local` synchronization.
   - Direct support for `AWS_REGION`, `S3_MEDIA_BUCKET` / `NEXT_PUBLIC_S3_MEDIA_BUCKET`, and `COGNITO_DOMAIN`.

## 2. Research Decisions & Architectural Rationale

### Research Topic 1: S3 Bucket Security & Public Access Block Strategy

- **Context**: Electa requires public read access to media assets for browsers and voters, while preventing unauthorized write or administrative actions.
- **Decision**: Keep the S3 bucket fully private with `aws_s3_bucket_public_access_block` enabled (`block_public_acls = true`, `block_public_policy = true`, `ignore_public_acls = true`, `restrict_public_buckets = true`).
- **Rationale**: Direct public buckets invite security vulnerabilities and configuration drift. By blocking public access at the S3 bucket level, all client writes are executed via time-limited pre-signed URLs generated by backend services using IAM credentials, and public reads can be served via CloudFront / CDN or public URLs without permitting public write or list privileges.
- **Alternatives Considered**:
  - *Public S3 Bucket with Read Policy*: Rejected due to AWS security compliance risks and inability to prevent unauthorized hotlinking or scraping without CDN protections.

---

### Research Topic 2: CORS Configuration for Browser Client Uploads

- **Context**: Web clients upload image files directly from browsers to S3 via pre-signed URLs. Browsers issue preflight `OPTIONS` requests before uploading.
- **Decision**: Configure `aws_s3_bucket_cors_configuration` with:
  ```json
  [
    {
      "AllowedHeaders": ["*"],
      "AllowedMethods": ["PUT", "POST", "GET", "HEAD"],
      "AllowedOrigins": [
        "http://localhost:3000",
        "https://*.electa.app",
        "https://*.electa.com"
      ],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3000
    }
  ]
  ```
- **Rationale**:
  - `PUT`, `POST` are required for pre-signed multi-part or single-part image uploads.
  - `GET`, `HEAD` are required for browser asset retrieval and client metadata checks.
  - Wildcard subdomain origins (`https://*.electa.app`, `https://*.electa.com`) accommodate dynamic preview deployments (Vercel/Amplify) and production subdomains.
  - Exposing `ETag` allows the browser client to verify upload checksum integrity upon completion.
- **Alternatives Considered**:
  - *Origin `*`*: Insecure for production; violates CORS security principles.
  - *Restricting to root domain only*: Breaks preview branches and local development.

### Research Topic 3: Least-Privilege IAM User vs. Direct Bucket Policy

- **Context**: The backend application needs AWS credentials to sign pre-signed upload URLs and manage media assets.
- **Decision**: Provision an IAM service user (`electa-s3-service-user`) with an attached IAM policy `ElectaS3MediaPolicy`:
  ```json
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "ElectaMediaBucketAccess",
        "Effect": "Allow",
        "Action": [
          "s3:PutObject",
          "s3:GetObject",
          "s3:DeleteObject"
        ],
        "Resource": "arn:aws:s3:::${bucket_name}/*"
      }
    ]
  }
  ```
- **Rationale**:
  - Follows AWS least-privilege security principle.
  - Denies destructive bucket operations (`s3:DeleteBucket`, `s3:PutBucketPolicy`, `s3:ListAllMyBuckets`).
  - Does not grant bucket-level listing (`s3:ListBucket`) to prevent metadata enumeration attacks.
- **Alternatives Considered**:
  - *Full S3 Access (`AmazonS3FullAccess`)*: Unacceptable security violation.
  - *IAM Role with OIDC*: Optimal for AWS EC2/ECS/EKS, but for hybrid local/Vercel serverless environments, IAM service user access keys or regional role delegation provide reliable portability.

---

### Research Topic 4: Application Environment Variable Schema & Validation

- **Context**: Next.js 16 requires client and server environment separation. Constitution §I and §IV mandate strict Zod validation without raw `process.env`.
- **Decision**: Extend `src/env.ts` with Zod validation for:
  - `AWS_REGION`: Server & client validation (defaults to `ap-southeast-1`).
  - `S3_MEDIA_BUCKET`: Validates bucket string format (supports both `S3_MEDIA_BUCKET` and `NEXT_PUBLIC_S3_MEDIA_BUCKET` alias for client display).
  - `COGNITO_DOMAIN`: Validates HTTPS domain format.
- **Rationale**: Fails fast during build/start if required environment keys are missing or malformed, preventing runtime silent failures.
